# 即時手機 Tracker：安全、失追與平滑計畫

**狀態：2026-11-06，receiver 的 tracker 輸出、安全門檻與自動測試已完成；本機手機即時 OSC 與 Avatar 動作已初驗。** 平滑、速度限制與失追後過渡仍在規劃中；即時腳別、遠端效果、精度與長時間穩定性尚未驗收。重新校正初始預設 250 ms，不是已驗證的最佳值。

`pose_receiver.py --output trackers` 要求當次確認的三個 ID、髖高、鏡像、左右標籤、前向與 yaw；預設 `none` 不送 OSC，舊 `--osc` 保留六參數。接收端只有完整可信、已校正的三角色 transform 才發送。低信心、無人、缺點或亂序不重設最後有效時間；失追與新 session 清除校正及最後姿勢。`T=--tracker-loss-ms` 可調，預設 250 ms、上限 5000 ms；`H=--tracker-hold-ms` 獨立，預設 0、上限 `min(T,250 ms)`。保守的每角色位移 0.5 m、yaw 最短角 90° 突變檢查會要求重校正；這些門檻尚未用真人即時資料調校。輸出錯誤會關閉 transport。自動測試含隔離 UDP，不向 VRChat 發送。

## 已證實

1. `tracker_pose.py` 已對必要點低信心、缺失與不合理座標拒絕輸出；`TrackerCalibrationConfig.loss_timeout_ms` 在程式設定中預設為 250 ms，超時清除校正。現有手機 tracker 預覽 CLI 沒有提供此門檻參數。
2. `pose_receiver.py` 預設不送 OSC；`--osc` 明確啟用六項 Avatar parameters，**不是** tracker 模式。`--output trackers` 已經透過 `tracker_bridge.py` 整合 `tracker_output.py`，通過自動測試與一次本機即時觀察。
3. 在 VR 模式、合成 HMD／雙控制器、AnyaDance 自帶 trackers 停用的條件下，已存手機 ZIP 的靜態姿勢在本機可見角色右腳抬起。每張照片間隔約 3 秒，不代表即時串流或連續動作通過。2026-11-06 該輪映射 1＝髖、3＝左腳、4＝右腳；下次不得假設相同。
4. 原始 ZIP 所選影格的估計右踝增量約 6.54 cm，使用者確認視覺上清楚，將未達 20 cm 對**本次視覺可見性**列為低風險；絕對公尺精度和其他動作仍未驗證。不以達到 20 cm 作為安全整合的門檻，也不自動放大高度。

## 已實作：輸出與可調整的失追門檻

1. 保留 receiver 的封包驗證、來源限制、ACK、session／序號檢查與六參數相容性。明確選擇 `--output none|parameters|trackers`；無額外選擇時為 `none`。既有 `--osc` 與新選擇衝突時明確拒絕。
2. `trackers` 必須明確提供已確認的髖／左腳／右腳相異 ID、髖高、鏡像、前向、左右標籤設定與初始 yaw；新鮮且可信的站姿校正完成前不輸出。每次先驗證整組三角色資料，再編碼發送；UDP 是多個 datagram，不能宣稱網路上的完整批次原子送達。
3. **重新校正門檻 `T` 由設定及 `--tracker-loss-ms` 提供，初始預設 250 ms。** 從最後一組完整有效 transform 的接收端單調時間起計，不是從收到任意封包或手機時鐘起計。檢查有限、正數及 5000 ms 上限；不支援執行中熱調整。
4. **短暫保持上限 `H` 與 `T` 分開。** `--tracker-hold-ms` 預設 `H=0`，不重複舊姿勢；明確設定正值時限制 `H ≤ min(T, 250 ms)`，來源失效不重設計時器。既有 receiver `--hold-ms` 只屬六參數路線。
5. 超過 `T`，或出現新 session／超出突變門檻時，停止 tracker 更新、清除校正與最後輸出姿勢，重新收集可信站姿後才可恢復。若 `H` 已到但 `T` 尚未到，先停止重送；在 `T` 內恢復仍須通過身分、信心、時間及突變檢查。狀態輸出包含校正中、追蹤中、暫停、失追。尚無平滑狀態可清除。

停止發送**不保證 VRChat 即時清除最後姿勢**；不要假設腳會立刻回到地面。程序結束、例外及輸出錯誤需關閉 transport，記錄狀態；處理實際遊戲殘留需另行驗證。預設不保存相片或原始 landmarks。

## 待實作／調校：避免突兀

1. 既有照片回放只在三個靜態姿勢間切換，天然會跳；不能用稀疏照片證明即時追蹤也有相同程度的抖動。即時模式只對**目前有效資料**做濾波，不用過期或低信心資料假造新追蹤。
2. 可先採使用實際時間差的位置低通濾波，規劃以約 100 ms 時間常數作初始測試值；yaw 要沿最短角度，例如 179° 到 -179° 是 2°，不是 358°。濾波強度與位移／角速度上限應可設定、可測試，避免不合理跳變；數值待量測，不能宣稱已適合所有動作。
3. `T` 內短暫中斷後，若同一 session、座標／角色一致且新資料可信、落差合理，可試以 **0.2–0.4 秒**向持續更新的目標柔和過渡。持續監控失效；低信心、超時或大幅跳躍時不要讓過渡延長 `H` 或覆蓋保護。若落差過大或品質不足，停止更新並要求重新校正，不直接跨越。
4. 相隔一秒的新舊姿勢不能還原失去的真實動作。當 `T=250 ms` 時，此情況已失追：先停更新、重校正，不應直接把一秒空白補成真人曾做過的路徑。未來若把 `T` 調長，仍受獨立保持上限 `H` 與可信恢復條件約束；調整 `T` 不代表允許自動跨越任意落差。
5. 指數低通可能增加延遲；可在有實測資料後比較 [One Euro Filter 論文](https://cristal.univ-lille.fr/~casiez/publications/hdrcasiez.pdf) 所描述的速度自適應方法。不要把候選濾波值、0.2–0.4 秒或某種濾波器視為已通過遊戲內驗收。

## 驗證與完成條件

1. 使用合成資料、假單調時鐘及隔離 loopback 埠，測試預設零 OSC、明確 tracker／六參數選擇、無效配置與 ID 對調，以及校正前不送。
2. 測試低信心、無人、缺點、無封包、亂序／重複、session 變更、超時、異常停止；確認無效資料不能延長最後有效時間，也不挪用上一幀當成新資料。
3. 測試 `T` 的預設 250 ms 及至少一個不同值、非法／邊界值；同時確認 `H` 的獨立上限在調大 `T` 後仍生效。測試 1 秒失追、超大跳躍、短暫恢復、yaw 跨 ±180°、速度上限與重校正後濾波狀態清除。
4. 視需要以已存的不同輪高頻 JSONL 進行離線檢查，不能把它與照片 ZIP 當同一輪，也不能由稀疏照片推斷即時延遲。程式變更後在 `windows` 執行 `python -B -m unittest discover -v`，並報告實際結果。
5. 自動檢查通過後仍不宣稱遊戲內已驗收。需要使用者更新 App 或配合實機前，先依其當輪指示以語音通知、預留就位時間；若當輪明確要求不用語音則遵照。真人測試排成完整一輪，結束後才請使用者回答。

後續驗證須確認 VRChat 自身為站姿模式、FBT 開關可用且目前 tracker ID 映射明確；前次的坐姿模式錯誤、探針逾時與新一輪成功紀錄見 [排查紀錄](FBT_DIAGNOSTIC_2026-11-06.md) 及 [實驗結果](TEST_RESULTS.md)。純 Desktop FBT、遠端手機動作與長時間穩定性仍待驗證；Unity smoke 仍受 License Client IPC timeout 阻擋。
